## About this document

This is a transcription of Khalti's public integration documentation for the
ePayment Checkout platform, known as KPG-2. It exists so that an implementation
can be written against a fixed, quotable contract instead of a recollection of
one.

Sources, retrieved 2026-09-21:

- <https://docs.khalti.com/khalti-epayment/>
- <https://docs.khalti.com/getting-started/>

**Upstream is authoritative.** Everywhere else in this repository the
documentation wins when it disagrees with the code. Here the rule inverts: if
this file and `docs.khalti.com` disagree, `docs.khalti.com` is right and this
file is stale. Re-read the source before trusting anything below that a request
has just contradicted.

This document describes only what Khalti does. What this repository does about
it is recorded in
[ADR 0005](../decisions/0005-khalti-lookup-is-the-only-verification.md) and
[payments](../features/payments.md).

## Overview

Khalti's documented flow:

1. A user visits the merchant's website to make a purchase.
2. A unique `purchase_order_id` is generated on the merchant's system.
3. The merchant makes a server-side payment request to Khalti with the
   `purchase_order_id`, the `amount` in paisa, and a `return_url`.
4. The user is redirected to the ePayment portal (for example
   `https://pay.khalti.com`).
5. After the user pays, a callback is made to the `return_url`.
6. The merchant website can optionally confirm the payment received, then
   proceeds with its own steps.

Two properties of this API shape every integration built on it:

- **There is no webhook.** Khalti does not make a server-to-server notification.
  The browser redirect to `return_url` is the only unsolicited signal, and it
  arrives only if the browser comes back.
- **Khalti instructs merchants to confirm with lookup.** Its own wording:
  "Please use the lookup API for the final validation of the transaction."

No SDK or plugin is required — the integration is HTTP POST from the server. A
merchant account is required.

## Authorization

HTTP authorization is done with an auth key passed in the request header:

```json
{
  "Authorization": "Key <LIVE_SECRET_KEY>"
}
```

Requests are `application/json`.

**The key is called `live_secret_key` in both dashboards.** Khalti's own
instruction: use the `live_secret_key` from **test-admin.khalti.com** during
sandbox testing, and the `live_secret_key` from **admin.khalti.com** for
production. The name does not distinguish the environments; the dashboard it was
copied from does.

Omitting the `Key ` prefix is a distinct failure from passing a wrong key — see
[Errors](#errors).

## Initiate

Every payment request is first initiated from the merchant as a server-side
`POST`. On success Khalti returns a unique request identifier, `pidx`, which is
used for every later reference to the payment.

| URL | Method | Authorization | Format |
| --- | --- | --- | --- |
| `/epayment/initiate/` | POST | Required | application/json |

### Payload fields

| Field | Required | Description |
| --- | --- | --- |
| `return_url` | Yes | Landing page after the transaction. Field must contain a URL. |
| `website_url` | Yes | The URL of the website. Field must contain a URL. |
| `amount` | Yes | Total payable amount excluding the service charge. Amount must be passed in Paisa. |
| `purchase_order_id` | Yes | Unique identifier for the transaction generated by merchant. |
| `purchase_order_name` | Yes | This is the name of the product. |
| `customer_info` | No | This field represents to whom the txn is going to be billed to. |
| `amount_breakdown` | No | Any number of labels and amounts can be passed, but the sum of `amount_breakdown.amount` must equal `amount`. |
| `product_details` | No | Number of sets is unlimited. |
| `merchant_*` | No | Any attribute whose name starts with `merchant_` is accepted as additional metadata and is returned in the success response payload. |

The documented minimum amount is **1000 paisa**, that is Rs. 10 — the error
text is "Amount should be greater than Rs. 10, that is 1000 paisa."

Khalti's own examples are inconsistent about the type of `amount`: the sample
payload below sends the integer `1300`, every code sample sends the string
`"1000"`, and one documented error is "A valid integer is required."

### Sample request

```json
{
  "return_url": "https://example.com/payment/",
  "website_url": "https://example.com/",
  "amount": 1300,
  "purchase_order_id": "test12",
  "purchase_order_name": "test",
  "customer_info": {
    "name": "Khalti Bahadur",
    "email": "example@gmail.com",
    "phone": "9800000123"
  },
  "amount_breakdown": [
    {
      "label": "Mark Price",
      "amount": 1000
    },
    {
      "label": "VAT",
      "amount": 300
    }
  ],
  "product_details": [
    {
      "identity": "1234567890",

      "quantity": 1,
      "unit_price": 1300
    }
  ],

```

```bash
    "return_url": "http://example.com/",

      "name": "Test Bahadur",

    }

```

### Success response

```json
{
  "pidx": "bZQLD9wRVWo4CdESSfuSsB",
  "payment_url": "https://test-pay.khalti.com/?pidx=bZQLD9wRVWo4CdESSfuSsB",
  "expires_at": "2023-05-25T16:26:16.471649+05:45",
  "expires_in": 1800
}
```

After a success response the user is redirected to the `payment_url`.

## Callback

The `return_url` must support `GET`. After the user completes or abandons the
payment, Khalti redirects the browser to it with these query parameters:

| Parameter | Description |
| --- | --- |
| `pidx` | The initial payment identifier |
| `status` | Status of the transaction |
| `transaction_id` | The transaction identifier at Khalti |
| `tidx` | Same value as `transaction_id` |
| `amount` | Amount paid in paisa |
| `total_amount` | Same value as `amount` |
| `mobile` | Payer KHALTI ID |
| `purchase_order_id` | The `purchase_order_id` provided during payment initiate |
| `purchase_order_name` | The `purchase_order_name` provided during payment initiate |

The success sample below also carries a `txnId` parameter, which Khalti's
parameter list does not mention. Treat anything outside the table above as
undocumented.

The `status` values documented for the callback:

| Value | Meaning |
| --- | --- |
| `Completed` | Transaction is success |
| `Pending` | Transaction is in pending state, request for lookup API |
| `User canceled` | Transaction has been canceled by user |

### Sample callbacks

Successful transaction:

```text
http://example.com/?pidx=bZQLD9wRVWo4CdESSfuSsB
&txnId=4H7AhoXDJWg5WjrcPT9ixW
&amount=1000
&total_amount=1000
&status=Completed
&mobile=98XXXXX904
&tidx=4H7AhoXDJWg5WjrcPT9ixW
&purchase_order_id=test12
&purchase_order_name=test
&transaction_id=4H7AhoXDJWg5WjrcPT9ixW
```

Canceled transaction — note that `transaction_id`, `tidx` and `mobile` arrive
present but empty:

```text
http://example.com/?pidx=bZQLD9wRVWo4CdESSfuSsB
&transaction_id=
&tidx=
&amount=1000
&total_amount=1000
&mobile=
&status=User canceled
&purchase_order_id=test12
&purchase_order_name=test
```

Khalti states that no further step is required to complete the payment, that a
merchant may run its own validation and confirmation steps, and that it is
recommended to check the lookup API for confirmation after the redirect callback
is received. Its emphasised note: "Please use the lookup API for the final
validation of the transaction."

## Lookup

After a callback is received, the `pidx` from initiation is used to look up and
reassure the payment status.

| URL | Method | Authorization | Format |
| --- | --- | --- | --- |
| `/epayment/lookup/` | POST | Required | application/json |

### Request

```json
{
  "pidx": "HT6o6PEZRWFJ5ygavzHWd5"
}
```

### Response fields

| Field | Description |
| --- | --- |
| `pidx` | The payment id of the transaction |
| `total_amount` | The total amount of the transaction |
| `status` | One of the seven values in the table below |
| `transaction_id` | The transaction id for the transaction; the unique identifier |
| `fee` | The fee that has been set for the merchant |
| `refunded` | `true` — the transaction has been refunded. `false` — it has not |

### Status, HTTP code and prescribed action

| Status | HTTP | Description | Khalti's prescribed action |
| --- | --- | --- | --- |
| `Completed` | 200 | Transaction is success | Provide service to user. |
| `Pending` | 200 | Transaction is failed or is in pending state | Hold, do not provide service. And contact Khalti team. |
| `Initiated` | 200 | — | — |
| `Refunded` | 200 | Transaction has been refunded | Transaction has been refunded to user. Do not provide service. |
| `Partially Refunded` | 200 | Transaction has been partially refunded by the user | — |
| `Expired` | 400 | This payment link has expired | User have not made the payment, Do not provide the service. |
| `User canceled` | 400 | Transaction has been canceled by the user | User have canceled the payment, Do not provide the service. |

`Initiated` and `Partially Refunded` appear in Khalti's status-code table but
have no row in its lookup-status table, and `Initiated` is described nowhere,
so no action is prescribed for either upstream. Those gaps are Khalti's, not
transcription omissions.

**Khalti spells the partial-refund status two ways.** Its status-code table
says `Partially Refunded` and its field-description table says
`Partially refunded`. Which one arrives on the wire is not documented.

### Khalti's important note

> - Only the status with **Completed** must be treated as success.
> - Status **Canceled**, **Expired**, **Failed** must be treated as failed.
> - If any negative consequences occur due to incomplete API integration or
>   providing service without checking lookup status, Khalti won't be
>   accountable for any such losses.
> - For status other than these, hold the transaction and contact **KHALTI**
>   team.
> - Payment link expires in 60 minutes in production.

`Canceled` and `Failed` in that note are not values this API returns — the
documented statuses are the seven in the table above. Read it as intent, not
as a list to match strings against.

## Errors

Validation failures on initiate carry an `error_key` of `validation_error`
alongside a DRF-style field-errors object.

`return_url` is blank:

```json
{
    "return_url": [
        "This field may not be blank."
    ],
    "error_key": "validation_error"
}
```

`return_url` is invalid:

```json
{
    "return_url": [
        "Enter a valid URL."
    ],
    "error_key": "validation_error"
}
```

`website_url` is blank:

```json
{
    "website_url": [
        "This field may not be blank."
    ],
    "error_key": "validation_error"
}
```

`website_url` is invalid:

```json
{
    "website_url": [
        "Enter a valid URL."
    ],
    "error_key": "validation_error"
}
```

Amount is less than Rs. 10:

```json
{
    "amount": [
        "Amount should be greater than Rs. 10, that is 1000 paisa."
    ],
    "error_key": "validation_error"
}
```

Amount is invalid:

```json
{
    "amount": [
        "A valid integer is required."
    ],
    "error_key": "validation_error"
}
```

`purchase_order_id` is blank:

```json
{
    "purchase_order_id": [
        "This field may not be blank."
    ],
    "error_key": "validation_error"
}
```

`purchase_order_name` is blank:

```json
{
    "purchase_order_name": [
        "This field may not be blank."
    ],
    "error_key": "validation_error"
}
```

Amount breakdown does not total the amount passed:

```json
{
    "amount": [
        "Amount Breakdown mismatch."
    ],
    "error_key": "validation_error"
}
```

### Generic errors

An incorrect authorization key:

```json
{
   "detail": "Invalid token.",
   "status_code": 401
}
```

The `Key ` prefix missing from the authorization header:

```json
{
    "detail": "Authentication credentials were not provided.",
    "status_code": 401
}
```

An unknown `pidx` passed to lookup:

```json
{
   "detail": "Not found.",
   "error_key": "validation_error"
}
```

Note the two envelopes differ: authentication failures carry `status_code`,
validation failures carry `error_key`.

## Not offered by this API

Absences that are properties of KPG-2 rather than of any particular integration:

- **No webhook or server-to-server notification.** The browser redirect is the
  only push channel, and lookup is the only pull channel.
- **No refund endpoint.** Lookup reports `Refunded` and `Partially Refunded`,
  but refunds are initiated from the Khalti merchant dashboard, not over this
  API.
- **Payment links expire.** 60 minutes in production; the sandbox initiate
  sample returns `expires_in: 1800`.
- **No card or e-banking in sandbox.** Those payment methods can only be
  exercised against production.
