# Deployment

Status: Implemented

Last updated: 2026-09-24

---

## Goal

Make the repository deployable, and write the deployment down once so it is not
reconstructed from memory each time. The service is a native Python web service on
Render, described by a blueprint in the repository rather than by settings typed
into a dashboard.

---

## Scope

What is included in this implementation?

- `render.yaml`, the whole service: build, start, health check, and every
  environment variable
- The production-only settings a platform deploy needs
- Guards that keep the blueprint and the settings from drifting apart
- The operational consequences of the free instance type

What is explicitly outside the scope?

- **Creating the service.** That needs the Render account. This makes the deploy
  possible and describes it; it does not perform it.
- Docker. Removed — see Decisions.
- Log drains, error tracking, alerting, uptime monitoring
- A staging environment. One service, one branch
- Custom domains and their TLS

---

## Context

Nothing had ever been deployed, and the repository could not be. The deploy path
was a `Dockerfile` whose `collectstatic` step supplied four environment variables,
while [ADR 0008](../decisions/0008-every-environment-variable-is-required.md)
requires all 37 at settings import. The image had not built since that decision
landed, and CI never ran `docker build`, so nothing said so.

**Dropping Docker removed the problem rather than solving it.** A native Render
build runs with the service's environment variables present, so `collectstatic`
gets exactly the configured environment ADR 0008 demands. Render also detects
`uv.lock` and uses uv, so the deploy honours `CLAUDE.md`'s "no pip, no Poetry, no
`requirements.txt`" without a workaround, and `.python-version` pins the
interpreter to 3.12 against a platform default that has since moved to 3.14.

The blueprint is the only place the production environment is written down. Two
tests keep it honest, because a variable that `base.py` requires and `render.yaml`
omits is a deploy that builds successfully and then fails at import.

---

## Implemented

- `render.yaml` — one `web` service, `runtime: python`, free plan, Singapore
  (nearest region to Supabase's `ap-northeast-2`), `healthCheckPath: /health/`,
  and all 38 variables: 17 prompted at setup, `DJANGO_SECRET_KEY` generated by
  Render, and 20 carrying values from the blueprint — one of them
  `DJANGO_SETTINGS_MODULE=config.settings.production`, see Decisions
- `config/settings/production.py` — appends `RENDER_EXTERNAL_HOSTNAME` to
  `ALLOWED_HOSTS`, and exempts `^health/` from the SSL redirect
- `docs/convention.md` — records the two environment-variable exceptions this
  creates, `RENDER_EXTERNAL_HOSTNAME` and `DJANGO_SETTINGS_MODULE`
- `.github/workflows/ci.yml` — `makemigrations --check --dry-run`, which
  `architecture.md` has always required and nothing enforced
- `Dockerfile` and `.dockerignore` — **deleted**. `docker-compose.yml` stays; it
  provides local Postgres and Redis and never was the deploy path
- `tests/test_settings.py` — the blueprint parity guards and the production
  settings assertions

---

## Remaining

- **No deploy has been verified end to end.** The service exists, and its first
  deploy failed on the staticfiles manifest (see Decisions). The fix has not yet
  been confirmed on Render; most claims here are still about configuration rather
  than observed behaviour.
- **No observability beyond Render's log stream.** No drain, no error tracking, no
  alerting. `../handover.md` is the manual substitute, and free-tier log retention
  is short enough that a complaint three days later may have no line left to find.
- **Migrations run in the build command**, because the free tier has no
  `preDeployCommand`. See Decisions.
- **No staging environment.** `main` deploys straight to the only service.

## Decisions

### Decision: a native Python service, not a container

**Decision**

`Dockerfile` and `.dockerignore` are deleted. Render builds the service from the
repository with its own Python runtime.

**Reason**

The container bought nothing here and cost the build. A Docker build does not get
the service's environment, so `collectstatic` had to be fed values some other way —
inline dummies that duplicate `config/settings/test.py` in a second language, a
fifth settings module written only for the build, or Render's build args, which its
own documentation warns bake into image layers and so must not carry secrets. A
native build has the real environment and needs none of that.

**Consequence**

The runtime is Render's rather than one this repository pins beyond
`.python-version`, and there is no artifact that can be run locally or elsewhere
identically. Both are acceptable while there is one service and one environment;
neither would be if this became several.

### Decision: migrations run in the build command

**Decision**

`buildCommand` runs `uv sync --frozen`, then `migrate --database=direct`, then
`collectstatic --noinput`.

**Reason**

`architecture.md` requires migrations to run once per deploy and never at boot, so
that two starting instances cannot race. Render's `preDeployCommand` is the right
place for that and is not available on the free instance type. The build command
also runs exactly once per deploy, so the race the rule exists to prevent does not
occur.

`--database=direct` because migrations cannot run over Supabase's pooler. This is
the repo-specific detail no Render guide covers.

**Consequence**

Migrations apply **before the release is known good**. A deploy that then fails to
start leaves a migrated database with the previous version serving it, so every
migration must be backward compatible with the release before it. Moving this to
`preDeployCommand` is the first thing to do on upgrading the instance type.

### Decision: `ALLOWED_HOSTS` learns the hostname from Render

**Decision**

`production.py` appends `RENDER_EXTERNAL_HOSTNAME` to whatever
`DJANGO_ALLOWED_HOSTS` lists.

**Reason**

Without it, every request is a `400 DisallowedHost` — including the platform health
check, so the deploy never goes live and the failure reads as an application crash
rather than a missing hostname. Render's own Django guide recommends exactly this.

It cannot go through `EnvironmentReader`: ADR 0008's readers require a variable to
be present, and this one exists only on Render. Appending rather than assigning
keeps a custom domain working.

**Consequence**

One `os.environ` read outside `base.py`, which `convention.md` records as an
exception. It lives in the settings module that is already Render-specific —
the same file sets `SECURE_PROXY_SSL_HEADER` for Render's proxy.

### Decision: the blueprint sets `DJANGO_SETTINGS_MODULE`

**Decision**

`render.yaml` declares `DJANGO_SETTINGS_MODULE=config.settings.production` as a
fixed value, so the build command and gunicorn load the same settings.

**Reason**

The build command runs `manage.py`, which falls back to `config.settings.local`,
while gunicorn loads `config/wsgi.py`, which falls back to `production`. `local`
uses `StaticFilesStorage`, which writes no `staticfiles.json`, so production's
`CompressedManifestStaticFilesStorage` raised
`Missing staticfiles manifest entry for 'admin/css/base.css'` on every page using
`{% static %}` — the admin first. `migrate` ran under `local` for the same reason.

An environment variable was chosen over `--settings` on each build command, so a
command added to the build later cannot forget it.

**Consequence**

`.env.example` lists the variable, because
`test_the_blueprint_declares_nothing_the_settings_ignore` requires every blueprint
key to be there. It is not required by ADR 0008 and cannot be — Django reads it
before `base.py` loads — and the value in `.env` is never honoured. `convention.md`
records it as the second exception.

## Gotchas

- **The free instance sleeps when idle.** The first request afterwards pays a cold
  start. The worst place that lands is the Khalti return: ADR 0005 calls the lookup
  *inline during that request*, so the slowest request in the system is the one
  where money has just changed hands. A customer may wait, or give up and refresh —
  which is safe, because verification is idempotent on `pidx`.
- **`DJANGO_CORS_ALLOWED_ORIGINS` is the one misconfiguration ADR 0008 cannot
  catch.** It is in `strict_env.MAY_BE_EMPTY`, so an empty value boots cleanly and
  the storefront is blocked by the browser on every request with **nothing in the
  backend logs**. It is `sync: false` in the blueprint so Render prompts for it.
- **`SECURE_REDIRECT_EXEMPT` is not cosmetic.** `DJANGO_SECURE_SSL_REDIRECT` is
  `True`, and `SecurityMiddleware` answers anything it does not consider secure
  with a 301. A health check arriving without `X-Forwarded-Proto: https` would get
  the redirect instead of a 200, and a correct deployment would look dead.
- **`--bind 0.0.0.0:$PORT`.** Render's default is 10000 and it only *usually*
  detects a different port; when detection fails, the deploy fails. The deleted
  Dockerfile hardcoded 8000 and relied on that detection.
- **`--timeout 30` is a floor, not headroom.** Khalti (10s) and SMTP (10s) are both
  spent inside the request by ADR 0005 and ADR 0006, and a Cloudinary upload is
  synchronous on top.
- **`--workers 2`**, because the free instance has 512 MB.
- **`Missing staticfiles manifest entry` means the build collected static files
  under the wrong settings.** Check that `DJANGO_SETTINGS_MODULE` is
  `config.settings.production` in the service's environment. A service created
  from the dashboard rather than synced from the blueprint does not receive
  blueprint `value:` entries; set it by hand, then clear the build cache and
  redeploy.
- **`healthCheckPath` is `/health/`, not `/health/ready/`.** Readiness returns 503
  when Redis is unavailable, which `architecture.md` says may happen at any time.
  Pointing the platform at it would recycle healthy containers over a cache blip.
- **Render and Supabase are in different regions** and every query crosses between
  them. An N+1 that is invisible locally is expensive here. Singapore is the
  nearest of Render's five regions to Supabase's `ap-northeast-2`.
- **The region cannot be changed after the service is created.** Render has no
  relocation: moving means a new service and migrating to it. It is the one
  value in `render.yaml` that is expensive to get wrong.

## Tests

- `test_the_blueprint_declares_every_required_variable` — every variable `base.py`
  reads is declared in `render.yaml`. Without it, a missing name is a successful
  build followed by a failed boot. Verified meaningful: removing one key from the
  blueprint fails it.
- `test_the_blueprint_declares_nothing_the_settings_ignore` — the other direction,
  so a stale key is not a value someone set on Render believing it did something.
- `test_the_blueprint_runs_the_build_under_production_settings` — guards the
  staticfiles-manifest failure above.
- `test_production_appends_the_render_hostname` and
  `test_production_leaves_allowed_hosts_alone_off_render`
- `test_production_exempts_the_health_endpoints_from_the_ssl_redirect`

The blueprint is matched with a regex rather than parsed: PyYAML is only a
transitive dependency here, and `pyproject.toml`'s note on `requests` is explicit
about importing those.

## Future context

The blueprint is the only description of the production environment that exists.
If it and the Render dashboard disagree, the dashboard is what is running — Render
does not reconcile a blueprint against a service that has drifted from it, and
nothing here detects that.

Three things move together on upgrading off the free tier: migrations to
`preDeployCommand`, the worker count, and the cold start that currently lands on
the payment return.

When observability is added, it is the same decision three ADRs are already
waiting on. ADR 0004, ADR 0005 and ADR 0006 each accept a failure mode with no
automatic recovery and no alert, and `../handover.md` asks a human to check for all
three daily. An error tracker would not replace those checks, but it would stop the
first sign of trouble being a customer.
